## Objective

Extend the basic authentication-failure counter from Lab 07 into a Python detector that identifies **repeated failed logins against the same account within a defined time window**. Practise log parsing, dictionaries, timestamps, conditional logic, alert deduplication, and validation.

## Part 1 — Controlled log dataset

Created `test-auth.log` with the following events:

```text
2026-11-17T10:00:00+00:00 auth: authentication failure user=alice
2026-11-17T10:00:20+00:00 auth: authentication failure user=alice
2026-11-17T10:00:45+00:00 auth: authentication failure user=alice
2026-11-17T10:05:00+00:00 auth: authentication failure user=bob
2026-11-17T10:07:00+00:00 auth: authentication failure user=bob
2026-11-17T10:08:00+00:00 auth: successful authentication user=alice
```

The dataset contains **five failed authentications** and **one successful authentication**. Alice's three failures occur over 45 seconds; Bob has only two failures, separated by two minutes.

## Part 2 — Detector implementation

Built on Lab 07's line-by-line file reading. The script:

1. Reads `test-auth.log` and selects lines containing `authentication failure`.
2. Extracts the account name from the `user=` field.
3. Uses an `accounts` dictionary to count failures per account.
4. Parses ISO 8601 timestamps using `datetime.fromisoformat()`.
5. Stores failure timestamps per account in a `times` dictionary.
6. Checks whether the **most recent three failures for an account** occurred within 60 seconds.
7. Adds the username to an `alerts` list to avoid duplicate alerts during the same run.
8. Prints an authentication-failure summary and the number of accounts flagged.

Core detection logic:

```python
if len(times[username]) >= 3 and username not in alerts:
    elapsed = (times[username][-1] - times[username][-3]).total_seconds()

    if 0 <= elapsed <= 60:
        alerts.append(username)
        print("ALERT:", username, "had 3 failures within 60 seconds")
```

This works with the test dataset because its events are in chronological order.

## Part 3 — Validation tests

Ran `python3 detector.py` under three conditions and verified the results:

| Test | Rule | Expected result | Observed result |
|---|---|---|---|
| 1. Positive detection | 3 failures within **60 s** | Alert for Alice only | **Passed** — 1 account flagged |
| 2. Negative detection | Change threshold to **30 s** | No alerts; Alice's 3 failures span 45 s | **Passed** — 0 accounts flagged |
| 3. Restored detection | Restore **60 s** threshold | Alice's alert returns | **Passed** — 1 account flagged |

The failure counts remained **Alice: 3**, **Bob: 2**, **total: 5**. The successful authentication event was excluded.

Expected report at the final 60-second setting:

```text
ALERT: alice had 3 failures within 60 seconds

--- Authentication Report ---
alice : 3 failed attempts
bob : 2 failed attempts
Authentication failures: 5
Accounts flagged: 1
```

## Findings and security relevance

- **A failure count alone is insufficient.** The time between failures helps distinguish sporadic mistakes from bursts worth investigating.
- **Per-account tracking matters.** Alice crosses the defined threshold; Bob does not.
- **Alert deduplication reduces noise.** The script reports an account only once per execution.
- **An alert is not proof of an attack.** Repeated failures are indicators that require context and investigation.

## Limitations

This is a **learning prototype**, not a production intrusion-detection system.

- It processes a **synthetic, fixed-format** log rather than continuously monitoring live authentication logs.
- It assumes chronological events and valid ISO 8601 timestamps.
- It assumes matching lines contain a `user=` field; malformed lines could cause errors.
- It alerts at most once per user for the entire script run, with no cooldown or repeat-incident handling.
- It does not correlate events by source IP, authentication service, or host.
- Detection thresholds are illustrative and would need tuning for a real environment.
